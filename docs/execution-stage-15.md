# Этап 15 — Исполнение сделок по подтверждению (BingX Perpetual Futures)

Статус: техзадание. Реализовывать по шагам 15.1 → 15.7, каждый шаг деплоится отдельно.

## 0. Решения пользователя (зафиксировано)

- Вход — **маркет-ордер сразу** после подтверждения
- **SL и TP выставляются на биржу** вместе со входом
- Объём — **авто из риск-профиля** (риск % ÷ расстояние до стопа)
- Точка входа — **только карточка сигнала**, ручного «открой мне BTC» нет
- Автоматического входа без человека нет и не будет. Кнопка «Да» — обязательное условие
- Наблюдение за этапом ведёт код и отчитывается сводкой, а не человек глазами (раздел 12а)

## 1. Границы модуля

Новый пакет `app/execution/`. Аналитика о нём не знает и не импортирует его.
Направление зависимостей строго одностороннее:

```
signals (analysis) → bot/handlers/execution → execution/service → exchanges/bingx
                                                   ↓
                                            trading/journal
```

`app/execution/` содержит:

```
app/execution/
├── models.py        OrderRequest, OrderResult, ExecutionRefusal (dataclasses)
├── sizing.py        расчёт количества, маржи, округление под биржу
├── guards.py        предторговые проверки, каждая — отдельная чистая функция
├── service.py       оркестратор: guards → sizing → exchange → journal
└── reconciler.py    сверка состояния биржи с журналом
```

Никакой торговой логики в handlers. Handler только собирает контекст и рисует кнопки.

Перед первой реальной отправкой ордера код обязан проверить, что ключ действительно

## 3. Тестовый контур — сначала демо

BingX даёт демо-торговлю фьючерсами на виртуальных USDT (VST) с отдельным API-хостом.

**Проверено этапом 15.4в** (через живой API, не по статье, как с тикерами):
`GET https://open-api-vst.bingx.com/openApi/swap/v2/quote/contracts` отвечает

Требование: базовый URL BingX-клиента выносится в конфиг:

```
BINGX_BASE_URL=https://open-api.bingx.com
BINGX_TRADING_MODE=demo|live
```

Первые дни исполнение гоняем на демо-ключе. Переключение того, куда РЕАЛЬНО уходят
ордера, — только через `.env` (`BINGX_TRADING_MODE`) и рестарт, кнопки «включить
реал» в интерфейсе нет и не будет.

**Этап 15.4в добавил другую кнопку** — не эту: переключатель «Счёт» в «Настройках»
меняет только то, какой счёт бот ЧИТАЕТ и ПОКАЗЫВАЕТ (баланс, позиции, карточка).
Если показ и `BINGX_TRADING_MODE` разойдутся, guard `MODE_NOT_ALLOWED` (раздел 7)
блокирует вход целиком — тихой отправки на «не тот» счёт нет.

```
Карточка сигнала READY
   [⚡ Открыть сделку]   [🔕 Пропустить]
        ↓
Карточка подтверждения (новое сообщение, не редактирование сигнала):
   BTC-USDT · LONG · маркет
   Цена сейчас: 63 240 (сигнал был на 63 180, дрейф 0.09%)
   Объём: 0.014 BTC ≈ 885 USDT нотионал

   Тейк: 65 100  RR 2.2
   Открытых позиций сейчас: 2 из 4
   Суммарный риск после входа: 2.8% из 5%

```

Карточка живёт **60 секунд**. По истечении кнопки заменяются на «Подтверждение

После исполнения — сообщение с фактической ценой входа, фактическим объёмом, комиссией
и ID ордеров SL/TP. Сделка автоматически появляется в журнале.

## 6. Расчёт объёма

Вход в `sizing.py`, всё на `Decimal`, переиспользует `trading/risk.py`, не дублирует его.

```
risk_amount    = deposit × risk_percent
stop_distance  = |entry − stop_loss|
raw_qty        = risk_amount / stop_distance
qty            = округление ВНИЗ до quantityPrecision символа
notional       = qty × entry
margin         = notional / leverage
```

Данные о символе (`quantityPrecision`, `pricePrecision`, `tradeMinQuantity`,
минимальный нотионал) берутся из `/openApi/swap/v2/quote/contracts` и кэшируются.
Округление только вниз — риск не может оказаться больше заявленного.

Отказ, если: `qty` после округления равен нулю, меньше минимального лота, нотионал ниже
минимального, или маржи не хватает.

## 7. Предторговые проверки (guards)

Каждая — отдельная функция, возвращает `None` или `ExecutionRefusal(code, message)`.
Выполняются по порядку, первая сработавшая останавливает вход:

1. `EXECUTION_DISABLED` — глобальный выключатель выключен
1а. `LIVE_ORDERS_NOT_ALLOWED` (раздел 16 ТЗ, шаг 15.5.1) — сразу после
    `EXECUTION_DISABLED`, до похода за правами ключа: реальные ордера на
    LIVE только по явному `EXEC_ALLOW_LIVE_MODE_ORDERS`, не как побочный
    эффект того, что `EXECUTION_DISABLED` уже `false`
    - `PERMISSIONS_UNKNOWN` (вне нумерации и вне `run_guards()`,
      проверяется один раз в `ExecutionService.evaluate()`, до похода за
      тикером) — не удалось проверить права ключа. До `NO_TRADING_KEY`:
      если права не удалось проверить, `key_can_trade_futures` мог
      остаться устаревшим значением — проверить его раньше, чем отказать
      этим кодом, значит рисковать пропустить `NO_TRADING_KEY` вместо
      честного «не знаем» или наоборот
    - `POSITION_MODE_UNKNOWN` (там же, раздел 16 ТЗ, шаг 15.5.1) — не
      удалось проверить режим позиций аккаунта
2. `NO_TRADING_KEY` — нет ключа или у него нет права на фьючерсы
3. `MODE_NOT_ALLOWED` — счёт, выбранный в настройках (LIVE/DEMO, раздел 15.4в),
   не совпадает со счётом, разрешённым конфигом (`BINGX_TRADING_MODE`)
3а. `SIGNAL_SUPERSEDED` (шаг 15.5.2а) — сканер записал в слот другой сетап
    после уведомления (`fingerprint` слота != `fingerprint` снимка). Слот
    погашен — `SIGNAL_EXPIRED`. См. раздел 8а
4. `SIGNAL_EXPIRED` — истёк снимок уведомления (`signal_notifications.expires_at`
   = `notified_at` + TTL сигнала; пересканы его не продлевают)
5. `SIGNAL_ALREADY_USED` — по этому уведомлению уже открывали
   (`signal_notifications.trade_opened_at`, не слот)
5а. `SETUP_ALREADY_TRADED` (шаг 15.5.2а) — по этому же сетапу (слот +
    `fingerprint`) уже открывали через другое уведомление: повторный вход в
    тот же сетап запрещён — наращивание риска

Проверки 3а-5а (идентичность сигнала) идут дёшево — сразу после
`MODE_NOT_ALLOWED` и до первого запроса к бирже: на «Да» по устаревшему
сетапу на биржу не уходит ни одного запроса.
6. `POSITION_EXISTS` — по символу уже есть открытая позиция. Сравнение
   намеренно только по символу, не по стороне: в one-way встречный ордер
   НЕТТО-ЗАКРЫВАЕТ (или переворачивает) открытую позицию — сравнение по
   символу это и ловит; в хедже встречный вход при уже открытой позиции —
   это ХЕДЖИРОВАНИЕ, которого в этом этапе нет (усреднение и докупки
   сознательно не делаем, раздел 15)
7. `MAX_POSITIONS` — превышен лимит одновременных позиций
8. `MAX_TOTAL_RISK` — суммарный риск открытых позиций + новая превысит лимит
9. `DAILY_LOSS_LIMIT` — дневной лимит убытка достигнут (логика уже есть в `daily_jobs`)
10. `PRICE_DRIFT` — цена ушла слишком далеко от цены на карточке подтверждения
11. `SIGNAL_STALE` (пакет B) — цена ушла от цены сигнала дальше порога в сторону
    тейка (одностороннее: движение к стопу не отказывает — либо его поймает
    `INVALID_LEVELS`, либо отказывать не за что)
12. `INVALID_LEVELS` — стоп по неверную сторону от входа, RR ниже минимального
13. `SIZE_TOO_SMALL` / `INSUFFICIENT_MARGIN` — из sizing
14. `SYMBOL_NOT_ALLOWED` — символ вне белого списка

Отдельно и жёстко: **риск после убытка не увеличивается ни при каких условиях**.
Мартингейла нет. Размер считается только от текущего депозита и фиксированного риск-процента.

## 8а. Идентичность сигнала (шаг 15.5.2а)

«Сигнал» в коде был строкой слота `signals (user, symbol, timeframe, level)`,
которую сканер перезаписывает на каждом скане: уровни, направление,
`fingerprint`, `expires_at`. Отсюда: «Да» исполнял текущие уровни слота, а не
показанные на карточке; старые кнопки открывали чужой сетап;
`SIGNAL_ALREADY_USED` навсегда сжигал слот; второй вход на слоте давал тот же
`client_order_id` и ложный UNIQUE; сводка считала слоты, а не события.

Решение — `signal_notifications`: одна строка на каждое **отправленное**
уведомление (READY и FORMING), неизменяемый снимок — `level`, `fingerprint`,
`setup`, `direction`, `entry_low/high`, `stop_loss`, `take_profit`,
`confidence`, `notified_at`, `expires_at` (= `notified_at` + TTL сигнала,
фиксирован). После вставки меняется только `trade_opened_at`.

- **Сканер:** вставка снимка в SAVEPOINT → flush (id) → отправка с кнопкой
  по `notification_id` → недоставка откатывает снимок. Коммит — один на весь
  проход. Если он не случится уже после отправки, кнопка укажет на id,
  которого нет, — хендлер ответит «Уведомление устарело»; sequence
  PostgreSQL не откатывается, id никогда не достанется другому уведомлению
- **Р1:** READY повторяется, когда истёк снимок **последнего уведомления**
  слота или его `fingerprint` отличается (иначе сетап, видимый непрерывно,
  после TTL стал бы недоступен: кнопка мертва, нового уведомления нет).
  FORMING — прежнее правило по слоту, без повтора раз в TTL
- **Кнопки:** `exn:open|yes|no:{notification_id}`. Старые
  `exec:open|yes|no:{signal_id}` из уже отправленных сообщений отвечают
  «Уведомление устарело — дождись нового сигнала» и ничего не исполняют
- **Карточка и «Да»** строятся из снимка: направление, вход, стоп, тейк,
  объём. Слот — только для проверок 3а-5а (раздел 7)
- **Идентичность входа:** `client_order_id = tj{notification_id}u{user_id}{E|S|T}`,
  Redis-лок `exec:lock:{user_id}:n{notification_id}`, ключ карточки в памяти,
  `execution_orders.notification_id`, `trades.notification_id` (писатель —
  15.5.4). `signals.trade_opened_at` код не читает и не пишет; колонка уходит
  отдельной миграцией
- **Р2:** на «Да» строка слота берётся `FOR NO KEY UPDATE` до гвардов, снимок
  перечитывается под блокировкой — два «Да» по разным уведомлениям одного
  сетапа сериализуются, второй получает `SETUP_ALREADY_TRADED`. NO KEY не
  мешает вставке снимков с FK на слот
- **Р3:** миграция ставит sequence `signal_notifications` выше `MAX(signals.id)`
  до бэкфилла — новый `tj{nid}u…` не совпадёт с `tj{signal_id}u…` сухих
  прогонов, записанных после деплоя 15.5.2
- **Сводка:** «Сигналов READY» — число отправленных READY-уведомлений в окне

Миграция `b0943282b974`: таблица, индексы `(signal_id, notified_at)` и
`(user_id, notified_at)`, бэкфилл по одной строке на строку `signals`
(`expires_at = COALESCE(notified_at, updated_at) + TTL сканера`,
`trade_opened_at = NULL` — «сожжённые» слоты оживают), колонки
`notification_id`. Downgrade переносит `trade_opened_at` из снимков обратно
в `signals`.

## 8. Идемпотентность и обрывы

Главная опасность: ордер ушёл на биржу, ответ не дошёл, код повторил — две позиции.

Порядок действий строго такой:

1. `client_order_id` детерминированный: `f"tj{signal_id}u{user_id}{role.letter}"`
   (раздел 16 ТЗ, шаг 15.5.2 — разделитель `u` и буква роли вместо `role.value`,
   иначе `(signal_id=12, user_id=3)` и `(signal_id=1, user_id=23)` совпадали бы),
   укладывается в лимит длины BingX
2. Запись в `execution_orders` со статусом `PENDING` **до** HTTP-запроса, коммит
3. Отправка ордера
4. Успех → `SUBMITTED`/`FILLED` + `exchange_order_id`; сетевая ошибка или таймаут →
   статус `UNKNOWN`, **повторной отправки нет**
5. `UNKNOWN` → поиск ордера по `clientOrderID`. Нашёлся → досогласовать статус.
   Не нашёлся → статус остаётся `UNKNOWN`, пользователю уведомление. Автоматической
   повторной отправки нет **никогда** — ни до, ни после шага 15.6. Причины: (1)
   повторная отправка — это вход без подтверждения человеком по цене, которую он не
   видел, что нарушает раздел 0; (2) «не нашёлся» в момент поиска не значит, что
   ордера нет — запрос мог дойти, а ответ потеряться. Окончательное «ордер не
   выставлен» ставит только reconciler (15.6) после выдержанного окна. Сигнал
   остаётся использованным, следующий шанс — следующий READY

Строка `PENDING` старше разумного окна (раздел 16 ТЗ, шаг 15.5.2: процесс упал
между коммитом `PENDING` и обработкой ответа биржи — коммит на шаге 2 и коммит
после ответа биржи разделены HTTP-запросом, между ними есть окно) — reconciler
(15.6) обязан разбирать её тем же способом, что и `UNKNOWN`: поиск по
`client_order_id`, без автоматической повторной отправки. Причины те же, что
и в пункте 5 выше — такая `PENDING` неотличима от «запрос ушёл, ответ потерялся».

Кнопка «Да» защищена от двойного нажатия: callback обрабатывается один раз, повторное
нажатие получает ответ «уже обрабатывается». Блокировка через Redis по ключу
`exec:lock:{user_id}:{signal_id}` с TTL (`Settings.confirm_lock_ttl_seconds`).

**Что на самом деле гарантирует единственность входа — не лок.** Redis-лок даёт
только быстрый ответ «уже обрабатывается» при обычном двойном тапе, пока ключ жив.
TTL — предохранитель на случай, если процесс умрёт до `RedisLock.__aexit__` (не
дождавшись его — тогда лок и не снялся бы штатно); он не гарантирует, что обработка
уложится в TTL: разведка перед 15.5 показала, что при реалистичных таймаутах биржи
путь подтверждения способен занять дольше TTL, и тогда ключ в Redis гаснет по
таймеру, пока процесс всё ещё легитимно работает. Второе нажатие в этом окне
успешно берёт лок и запускает второй, полностью параллельный `_process_confirm` —
и гвард `SIGNAL_ALREADY_USED` эту гонку не ловит: `signal.trade_opened_at`
проставляется только после успешной записи строк заказа, то есть позже, чем
может успеть стартовать второй процесс.

Настоящая гарантия — шаг 2 выше: `UNIQUE` на `execution_orders.client_order_id`.
Он детерминированный (`f"tj{signal_id}{user_id}{role}"`), поэтому оба параллельных
процесса по одному сигналу вычисляют один и тот же ключ и оба пытаются вставить
строку с ним — тот, что делает это вторым, получает нарушение `UNIQUE` на `INSERT`
и должен ответить пользователю «уже обрабатывается», а не упасть необработанным
исключением.

**Важно для 15.5**: это работает, только если запись `PENDING`-строки с
`client_order_id` коммитится **до** любого обращения к бирже (см. шаг 2). Сегодняшний
DRY_RUN-путь (шаг 15.4, `app/bot/handlers/execution.py`) пишет строки `execution_orders`
**после** того, как `OrderRequest` уже построен — это нормально для сухого прогона
(похода на биржу там нет вообще), но **этот порядок нельзя копировать в 15.5**: если
запись PENDING встанет после отправки ордера, `UNIQUE` сработает только тогда, когда
оба параллельных процесса уже отправили ордер на биржу, и единственной защитой от
двойного входа останется дедуп биржи по `clientOrderID` — а он в этом проекте нигде
не подтверждён живым запросом.

**Открытый вопрос, решить на 15.5**: детерминированный `client_order_id` намертво
блокирует повторную попытку входа по тому же сигналу после отказа биржи (например,
«недостаточно маржи», пользователь пополнил баланс и хочет повторить) — тот же
`client_order_id` уже занят строкой с финальным статусом отказа. Нужно решение:
разрешать переиспользование ключа после явного финального статуса (`REJECTED`/`ERROR`),
либо вводить версию/суффикс попытки в `client_order_id`.

## 9. SL и TP на бирже

BingX v2 позволяет передать `takeProfit` и `stopLoss` JSON-строками прямо в запросе
на вход — **проверить актуальный формат по живой документации/API перед реализацией**,
не по статьям в интернете.

Порядок:

1. Аккаунт — в хедж-режиме (раздел 16 ТЗ, шаг 15.5.1: `GET .../positionSide/dual`,
   `dualSidePosition = true`, проверено живым запросом на демо 22.09; перед 15.7
   перечитать на боевом хосте — демо и боевой независимы). `positionSide` = `LONG`
   или `SHORT` по стороне сделки, не `BOTH`
2. Выставить плечо (`/openApi/swap/v2/trade/leverage`) до входа — только при
   расхождении с текущим плечом по нужной стороне (`get_leverage()` /
   `leverage_needs_update()`, раздел 16 ТЗ, шаг 15.5.1): в хедже плечо LONG и
   SHORT независимо, сравнивать нужно только ту сторону, что реально спросят при входе
3. Отправить маркет-ордер вместе с SL и TP

Если биржа приняла вход, но отклонила SL — это **аварийная ситуация**: позиция открыта
без стопа. Поведение: немедленно повторить постановку стопа отдельным условным ордером;
если и это не удалось — громкое уведомление «⚠️ ПОЗИЦИЯ БЕЗ СТОПА, символ, объём,
поставьте стоп руками» и запись в лог уровня ERROR. Не молчать, не ретраить бесконечно.

### 9а. Как это устроено (шаг 15.5.3)

- **Уровни до отправки** округляются до `pricePrecision` символа **к цене входа**
  (раздел 6: риск не больше заявленного): LONG — стоп вверх, тейк вниз; SHORT —
  стоп вниз, тейк вверх. Объём считается от уже округлённого стопа. На биржу
  уходит ровно то значение, по которому read-back потом ищет свой стоп
- **Тип триггера** — `CONDITIONAL_WORKING_TYPE = MARK_PRICE`, одна константа для
  вложенных TP/SL входа и для спасения
- **Read-back** — `app/execution/readback.py::verify_entry`, идемпотентна (всё
  состояние — в строках `execution_orders`), её же переиспользует reconciler 15.6:
  - SUBMITTED → `get_order_fill` по `clientOrderID`, до
    `EXEC_ORDER_READBACK_ATTEMPTS` (3) × `EXEC_ORDER_READBACK_DELAY_MS` (500).
    Разбор **строгий**: нет `orderId`/`status`/`avgPrice`/`origQty`/`executedQty`/
    `commission` → `ReadbackIncomplete`, не ноль. Вход FILLED, если биржа сказала
    FILLED; `executedQty < origQty` — предупреждение, стоп всё равно проверяется
  - UNKNOWN → один поиск после `EXEC_UNKNOWN_SEARCH_DELAY_MS`; нашёлся — дальше
    как SUBMITTED; нет — остаётся UNKNOWN, повторной отправки нет
  - стоп и тейк — среди `openOrders` (`find_our_conditional`): тот же символ,
    тип `STOP_MARKET`/`TAKE_PROFIT_MARKET`, наша `positionSide`, закрывающая
    сторона, `stopPrice` верхнего уровня = уровню из запроса до шага цены,
    создан не раньше входа (−5 с), `orderId` не занят другим входом, чужой
    `tj…` — не наш. Ровно один — наш; два и больше — «не могу отличить», без
    спасения. Строки S/T получают `client_order_id tj{nid}u{uid}S/T` — наша
    метка идемпотентности; сверка с биржей — по `exchange_order_id`
  - «стопа нет» — только после повторного чтения `openOrders` через
    `EXEC_OPEN_ORDERS_RECHECK_DELAY_MS` (вложенный стоп может стать отдельным
    ордером не сразу); `openOrders` не прочитан — без спасения вслепую, тревога
    «⚠️ СТОП НЕ ПОДТВЕРЖДЁН» и строка `STOP_LOSS` в ERROR `STOP_UNVERIFIED`
  - спасение — одна попытка `STOP_MARKET`/`TAKE_PROFIT_MARKET` с
    `closePosition=true` (без объёма — не зависит от частичного исполнения), та
    же дисциплина, что у входа: PENDING → commit → HTTP → commit, UNKNOWN не
    переотправляется. Провал стопа — тревога отдельным сообщением + ERROR в лог
    + аномалия сводки; провал тейка — обычное уведомление
- **Под локом** (решение владельца, вариант A): TTL = ceil(10 × (14+1)) + 10 +
  ceil(2.5) = **163 с** (см. `Settings.confirm_lock_ttl_seconds`)
- **Пользователю** — «⏳ Ордер отправлен, проверяю исполнение…», затем итог в том
  же сообщении: цена против карточки (проскальзывание словами — в худшую/лучшую
  сторону по направлению сделки), объём, комиссия, стоп и тейк с id
- Форма ответа `get_order` по исполненному маркету и условники верхнего уровня в
  `openOrders` живьём не сняты — фикстуры помечены «СИНТЕТИКА ДО 15.5.5»

### 9б. Сделка в журнале (шаг 15.5.4)

Журнал — не только история: POSITION_EXISTS / MAX_POSITIONS / MAX_TOTAL_RISK
считают открытые позиции по `trades`. Позиция на бирже без строки в журнале —
гварды слепы. Поэтому `app/execution/journal_entry.py::record_entry_trade` пишет
сделку после read-back под тем же локом при любом исходе входа, кроме отказа
(REJECTED / REFUSED / LEVERAGE_FAILED) и сухого прогона:

- **FILLED** — факт: `entry_price = avgPrice`, `quantity = executedQty`,
  `fees = commission`, `opened_at` — время исполнения из ответа (мягко:
  `updateTime`/`time`, нет — момент чтения), `fill_confirmed = true`
- **не подтверждено** (ReadbackIncomplete, SUBMITTED без FILLED, UNKNOWN) —
  предварительная сделка: плановая цена и объём, `fill_confirmed = false`,
  пометка в `notes`. Ложная блокировка символа до сверки безопаснее второй
  позиции; reconciler 15.6 ищет `source='SIGNAL_EXECUTION' AND
  fill_confirmed = false`
- стоп и тейк — реально стоящие на бирже (найденные/спасённые read-back);
  иначе плановый уровень и «стоп/тейк на бирже не подтверждён» в `notes`
- вход за уровнем стопа (проскальзывание) — сделка без стопа, пометка,
  ERROR в лог и отдельное тревожное сообщение
- `risk_percent`/`risk_reward` — из ордера (то, что пропустили гварды),
  `strategy_id` — по имени сетапа, `is_annotated = true`, если стратегия нашлась
- идемпотентность: `execution_orders.trade_id` у ENTRY + частичный уникальный
  индекс `uq_trades_notification_id` (миграция `0662dd79bd76`, там же
  `fill_confirmed BOOLEAN NOT NULL DEFAULT true`)
- **импорт истории** пропускает исполнения ордеров бота (`Fill.order_id` ∈
  `execution_orders.exchange_order_id`) — иначе импорт завёл бы вторую сделку
  на ту же позицию. Исполнение без `orderId` импортируется с warning «возможен
  дубль»
- на карточке открытой сделки бота — «закрывай в журнале только после закрытия
  позиции на BingX» (автозакрытие — 15.6). Монитор позиций сделки не закрывает,
  только уведомляет о приближении к TP/SL

## 10. Сверка с биржей (reconciler)

Расширяет существующий `position_monitor`, отдельный воркер, интервал ~1 минута:

- Тянет открытые позиции и последние ордера
- `execution_orders` в статусе `UNKNOWN` — доразрешает по `client_order_id`
- Позиция закрылась по SL или TP → закрывает сделку в журнале: фактическая цена выхода,
  комиссии, `exit_reason = STOP_LOSS | TAKE_PROFIT`, уведомление
- Позиция закрыта руками на бирже → сделка в журнале тоже закрывается, помечается
  как закрытая вне бота
- Расхождение «в журнале открыто, на бирже нет» → уведомление, а не тихая правка

Журнал остаётся источником истории, биржа — источником истины по текущему состоянию.

## 12а. Наблюдение — ежедневная сводка исполнения

Между шагами 15.4 и 15.7 нужен период наблюдения. Чтобы он не превратился в «человек
должен постоянно смотреть», наблюдение автоматизируется: код накапливает факты, бот
отправляет одну сводку в сутки.

Реализуется на шаге **15.4** (когда ордера ещё не уходят) и живёт дальше без изменений.

**Что записывается по каждому сигналу READY:**

- сам факт READY — момент, когда сканер уведомил о сетапе (`signals.notified_at`),
  независимо от того, что случилось дальше
- показана ли карточка подтверждения (карточка появляется, только если гварды до неё
  пропустили; отказ гварда до карточки — отдельный исход, карточка при нём не рисуется)
- решение пользователя: подтвердил / отказался / карточка истекла по TTL
- если отказ кода — `finding_code` гварда, который сработал, и **на какой стадии**:
  `evaluate()` вызывается дважды — при построении карточки (`stage=card`, карточки ещё
  нет) и на «Да» (`stage=confirm`, карточка уже показана). Отказ на «Да» — это показанная
  карточка, а не отказ «до карточки». Пересчёт после `PRICE_DRIFT` — построение новой
  карточки (`card`)
- сбой биржи на пути входа (`ExchangeError` и наследники: ключ, сеть, лимиты) — статус
  `ERROR`, тоже с `stage`. Это не отказ гварда и не `UNKNOWN`: вызов упал до отправки
  ордера. В `error_code` — имя класса исключения, `error_message` пуст (в тексте ошибки
  может быть тело ответа биржи), полный текст — в лог
- расчётные цифры на момент карточки: цена, дрейф от цены сигнала, объём, нотионал,
  маржа, плечо, риск в валюте и процентах, RR
- на шаге 15.4 — что именно ушло бы на биржу (готовый `OrderRequest` в лог и в
  `execution_orders` со статусом, помечающим «сухой прогон»)

**Сводка раз в сутки (`daily_jobs`, час из `EXEC_DAILY_DIGEST_HOUR`).** Окно данных —
скользящие 24 часа до момента отправки, не календарные сутки: час отправки не обязан
совпадать с локальной полночью, и календарные сутки резали бы события между часом
отправки и полночью — они не попадали бы ни в сегодняшнюю сводку (её уже нет), ни в
завтрашнюю (окно уже следующего дня).

«Сигналов READY» — счётчик из `signals` (сколько раз READY реально дошёл до пользователя
уведомлением за окно), а не из `execution_orders` — иначе READY-сигнал, упёршийся в отказ
гварда до карточки, был бы не виден в этой строке вовсе:

```
📊 Исполнение за последние 24 часа

Сигналов READY: 9
  показана карточка: 7
    подтверждено: 2
    отказ пользователя: 3
    истекло по TTL: 1
    отказ кода при подтверждении: 1
      PRICE_DRIFT — 1
    сбой биржи при подтверждении: 0
  отказ кода до карточки: 2
    MAX_POSITIONS — 2
  сбой биржи до карточки: 0

Средний расчётный риск: 0.9% (диапазон 0.7–1.0%)
Средний RR: 2.1
Средний дрейф цены на подтверждении: 0.12%

Аномалии: нет
```

Раздел «Аномалии» — главный. Туда попадает то, что человек глазами не поймает:

- расчётный риск отклонился от заданного больше чем на 10% (считается по каждой сделке
  отдельно, минимума выборки не требует)
- объём после округления даёт риск меньше половины заданного — слишком мелкий лот
  (тоже по каждой сделке отдельно)
- дрейф цены при подтверждении регулярно выше половины допустимого порога — не считается,
  пока карточек с данными о дрейфе меньше 3 (иначе одна-две сделки с шумом читаются как
  «регулярно»)
- гвард срабатывает подозрительно часто (более половины попыток за окно) — не считается,
  пока попыток меньше 5 (иначе один отказ на одну попытку — 100% — печатается как
  «подозрительно часто»). Код считается по обеим стадиям вместе. В знаменатель не входят
  сбои биржи: они случаются до гвардов, и с ними в знаменателе правило замолкало бы
  как раз во время сбоя биржи
- сбой биржи на пути входа (статус `ERROR`) — любой, минимума выборки нет: печатается
  число сбоев из всех попыток и разбивка по классу исключения
- на шагах 15.5+ — расхождения между журналом и биржей, найденные reconciler

Строки воронки печатаются всегда, в том числе с нулём: человек должен видеть, что
проверка была. Разбивка по кодам — только ненулевая. «Показана карточка» — сумма трёх
исходов самой карточки плюс попытки, оборвавшиеся на «Да» (отказ гварда или сбой биржи
на втором вызове `evaluate()`). Одна строка `execution_orders` — одна попытка.

Если аномалий нет — так и пишем. Пустая строка тут не годится: человек должен видеть,
что проверка была и прошла.

**Отчёт по демо-периоду.** На шаге 15.6 reconciler дополнительно умеет собрать сводный
отчёт за произвольный период: сколько входов, сколько закрыто по SL, по TP, вручную,
фактический средний R, расхождения с журналом. Вызывается кнопкой, руками ничего не сводится.

**Роль человека сокращается до трёх действий:** посмотреть цифры в карточке перед «Да»,
раз в сутки прочитать сводку, среагировать на раздел «Аномалии».

## 13. Тесты

Обязательно до включения на реальном счёте:

- `sizing`: округление вниз, минимальный лот, нехватка маржи, нулевое расстояние до стопа
- каждый guard отдельно, включая порядок срабатывания
- идемпотентность: повтор при `UNKNOWN` не создаёт вторую позицию (мок биржи)
- «вход прошёл, стоп отклонён» → уведомление и попытка восстановления
- reconciler: закрытие по SL, по TP, ручное закрытие на бирже, расхождение
- переход сигнал → ордер → сделка в журнале с корректным `entry_reason` из сигнала
- сводка исполнения: подсчёты по подтверждениям и отказам, срабатывание каждого
  правила из раздела «Аномалии» (включая минимум выборки), корректная сводка при нуле
  сигналов за окно, окно — ровно последние 24 часа, а не календарные сутки

BingX-клиент в тестах замокан полностью. Ни один тест не ходит на биржу.

## 15. Что сознательно не делаем

- Автоматический вход без подтверждения человеком
- Усреднение, докупки, увеличение риска после убытка
- Лимитные ордера и частичные входы — позже, если понадобится
- Трейлинг-стоп — позже
- Перенос стопа в безубыток автоматически — позже, отдельной задачей
- Закрытие позиции кнопкой из бота — отдельная задача, не в этом этапе
- Отправка ордера на биржу из формы «📝 Добавить сделку». Ручной ввод
  остаётся записью в журнал постфактум и не имеет ни одного из гвардов
  раздела 7. Вход не по сигналу, если понадобится, делается отдельной
  кнопкой через тот же execution/service.py — это этап 16, не правка
  формы журнала.

## 16. Проверить по живому API перед кодом

Не по статьям и не по памяти — как с тикером GRAMTON:

- хост демо-контура и работает ли на нём тот же ключ или нужен отдельный
- точный формат `takeProfit` / `stopLoss` в запросе на вход — **открыто**,
  закрывается на шаге 15.5.5 (первый демо-ордер, он же разведка)
- лимит длины `clientOrderID` и допустимые символы — **открыто**, туда же, на 15.5.5
- режим позиций аккаунта и корректный `positionSide` — **закрыто живьём 22.09**
  (раздел 16 ТЗ, шаг 15.5.1): `GET /openApi/swap/v1/positionSide/dual` (**v1**, не
  v2 — v2 отвечает `code 100404` "this api is not exist"), `data.dualSidePosition
  = true`, аккаунт в хедже. Перед 15.7 перечитать на **боевом** хосте — демо и
  боевой аккаунты независимы
- поля точности в `/openApi/swap/v2/quote/contracts` — **закрыто живьём 22.09**:
  точности (`pricePrecision`/`quantityPrecision`) там есть, а `maxLongLeverage`
  эта ручка не отдаёт вовсе; максимум плеча — из `GET /openApi/swap/v2/trade/leverage`
  (`LeverageInfo`)
- как в ответе приходит фактическая цена исполнения и комиссия маркет-ордера —
  **открыто**, закрывается на 15.5.5
- `allOrders`: окно запроса ≤ 7 дней, за пределами — `code 109400` — **закрыто
  живьём 22.09**
- `apiRestrictions`: в ответе нет ключей `code`/`msg` (в отличие от остальных
  ручек) — **закрыто живьём 22.09**
- **вопрос закрыт (14.09, `code 100001` "Signature verification failed due
  to signature mismatch" на запросах с `takeProfit`/`stopLoss`, обычный
  вход без TP/SL проходил тем же ключом):** причина — `_build_signed_query()`
  кодировала строку параметров целиком (`urlencode()`) и только потом
  подписывала уже закодированный результат. Официальная документация
  BingX требует обратного порядка: подпись считается по СЫРОЙ строке
  параметров, URL-кодирование (только значений, не ключей и не строки
  целиком) применяется отдельно, уже после подписи, только к тому, что
  реально уходит в запрос — раздел "Signature Description"
  (https://bingx-api.github.io/docs/#/en-us/swapV2/authentication.html
  #Signature%20Description) и детальный пример со значением-JSON —
  раздел "Place multiple orders" (https://bingx-api.github.io/docs/#/
  en-us/swapV2/trade-api.html#Bulk%20order). Для простых значений
  (`BTC-USDT`, `BUY`, числа) кодирование ничего не меняет, поэтому старый
  порядок не был заметен ни на одной другой подписанной ручке — расходился
  только `takeProfit`/`stopLoss`, единственные параметры со значением-JSON
  (спецсимволы `{`, `"`, `:`, `,` меняются при кодировании). Исправлено
  в `app/exchanges/bingx.py:_build_signed_query()` — см. докстринг метода.
