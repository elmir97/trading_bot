# Этап 15 — Исполнение сделок по подтверждению (BingX Perpetual Futures)

Статус: техзадание. Реализовывать по шагам 15.1 → 15.7, каждый шаг деплоится отдельно.

## 0. Решения пользователя (зафиксировано)

- Вход — **маркет-ордер сразу** после подтверждения
- **SL и TP выставляются на биржу** вместе со входом
- Объём — **авто из риск-профиля** (риск % ÷ расстояние до стопа)
- Точка входа — **только карточка сигнала**, ручного «открой мне BTC» нет
- Автоматического входа без человека нет и не будет. Кнопка «Да» — обязательное условие
- Наблюдение за этапом ведёт код и отчитывается сводкой, а не человек глазами (раздел 12а)

## 1. Границы модуля

Новый пакет `app/execution/`. Аналитика о нём не знает и не импортирует его.
Направление зависимостей строго одностороннее:

```
signals (analysis) → bot/handlers/execution → execution/service → exchanges/bingx
                                                   ↓
                                            trading/journal
```

`app/execution/` содержит:

```
app/execution/
├── models.py        OrderRequest, OrderResult, ExecutionRefusal (dataclasses)
├── sizing.py        расчёт количества, маржи, округление под биржу
├── guards.py        предторговые проверки, каждая — отдельная чистая функция
├── service.py       оркестратор: guards → sizing → exchange → journal
└── reconciler.py    сверка состояния биржи с журналом
```

Никакой торговой логики в handlers. Handler только собирает контекст и рисует кнопки.

## 2. Ключи BingX — важное изменение

Раньше договаривались про read-only ключ. Для исполнения нужен ключ с правом
**Perpetual Futures Trading**. Требования:

- Права: Read + Perpetual Futures Trading. **Withdraw и Universal Transfer — выключены**
- IP whitelist: `147.45.111.10` — обязательно, без исключений
- Ключ пересоздать заново, старый read-only удалить

Перед первой реальной отправкой ордера код обязан проверить, что ключ действительно
имеет право на торговлю, и внятно сообщить, если нет.

**Этап 15.4в:** ключ теперь принадлежит режиму (LIVE/DEMO), не только бирже — у
пользователя может быть по одной паре ключей на каждый режим (`exchange_credentials`,
`UNIQUE(user_id, exchange, mode)`). Заводятся, заменяются и удаляются раздельно в
«Настройках». Подробности — пункт 15.4в в разделе 14 ниже.

## 3. Тестовый контур — сначала демо

BingX даёт демо-торговлю фьючерсами на виртуальных USDT (VST) с отдельным API-хостом.

**Проверено этапом 15.4в** (через живой API, не по статье, как с тикерами):
`GET https://open-api-vst.bingx.com/openApi/swap/v2/quote/contracts` отвечает
`200` с реальным списком контрактов — хост рабочий. Нужен ли для него отдельный
ключ (а не тот же, что на боевом хосте) живым запросом не проверялось (нет
тестового ключа под рукой на момент реализации) — архитектура на этот вопрос
не полагается: `exchange_credentials` с самого начала хранит раздельную пару
ключей на LIVE и на DEMO (раздел 2), так что ответ "нужен свой ключ" уже учтён.

Требование: базовый URL BingX-клиента выносится в конфиг:

```
BINGX_BASE_URL=https://open-api.bingx.com
BINGX_TRADING_MODE=demo|live
```

Первые дни исполнение гоняем на демо-ключе. Переключение того, куда РЕАЛЬНО уходят
ордера, — только через `.env` (`BINGX_TRADING_MODE`) и рестарт, кнопки «включить
реал» в интерфейсе нет и не будет.

**Этап 15.4в добавил другую кнопку** — не эту: переключатель «Счёт» в «Настройках»
меняет только то, какой счёт бот ЧИТАЕТ и ПОКАЗЫВАЕТ (баланс, позиции, карточка).
Если показ и `BINGX_TRADING_MODE` разойдутся, guard `MODE_NOT_ALLOWED` (раздел 7)
блокирует вход целиком — тихой отправки на «не тот» счёт нет.

и ID ордеров SL/TP. Сделка автоматически появляется в журнале.

## 6. Расчёт объёма

Вход в `sizing.py`, всё на `Decimal`, переиспользует `trading/risk.py`, не дублирует его.

```
risk_amount    = deposit × risk_percent
stop_distance  = |entry − stop_loss|
raw_qty        = risk_amount / stop_distance
qty            = округление ВНИЗ до quantityPrecision символа
notional       = qty × entry
margin         = notional / leverage
```

Данные о символе (`quantityPrecision`, `pricePrecision`, `tradeMinQuantity`,
минимальный нотионал) берутся из `/openApi/swap/v2/quote/contracts` и кэшируются.
Округление только вниз — риск не может оказаться больше заявленного.

Отказ, если: `qty` после округления равен нулю, меньше минимального лота, нотионал ниже
минимального, или маржи не хватает.

## 7. Предторговые проверки (guards)

Каждая — отдельная функция, возвращает `None` или `ExecutionRefusal(code, message)`.
Выполняются по порядку, первая сработавшая останавливает вход:

1. `EXECUTION_DISABLED` — глобальный выключатель выключен
2. `NO_TRADING_KEY` — нет ключа или у него нет права на фьючерсы
3. `MODE_NOT_ALLOWED` — счёт, выбранный в настройках (LIVE/DEMO, раздел 15.4в),
   не совпадает со счётом, разрешённым конфигом (`BINGX_TRADING_MODE`)
4. `SIGNAL_EXPIRED` — сигналу больше его TTL
5. `SIGNAL_ALREADY_USED` — по этому сигналу уже открывали
6. `POSITION_EXISTS` — по символу уже есть открытая позиция
7. `MAX_POSITIONS` — превышен лимит одновременных позиций
8. `MAX_TOTAL_RISK` — суммарный риск открытых позиций + новая превысит лимит
9. `DAILY_LOSS_LIMIT` — дневной лимит убытка достигнут (логика уже есть в `daily_jobs`)
10. `PRICE_DRIFT` — цена ушла слишком далеко
11. `INVALID_LEVELS` — стоп по неверную сторону от входа, RR ниже минимального
12. `SIZE_TOO_SMALL` / `INSUFFICIENT_MARGIN` — из sizing
13. `SYMBOL_NOT_ALLOWED` — символ вне белого списка

Отдельно и жёстко: **риск после убытка не увеличивается ни при каких условиях**.
Мартингейла нет. Размер считается только от текущего депозита и фиксированного риск-процента.

## 8. Идемпотентность и обрывы

Главная опасность: ордер ушёл на биржу, ответ не дошёл, код повторил — две позиции.

Порядок действий строго такой:

1. `client_order_id` детерминированный: `f"tj{signal_id}{user_id}{role}"`, укладывается
   в лимит длины BingX
2. Запись в `execution_orders` со статусом `PENDING` **до** HTTP-запроса, коммит
3. Отправка ордера
4. Успех → `SUBMITTED`/`FILLED` + `exchange_order_id`; сетевая ошибка или таймаут →
   статус `UNKNOWN`, **повторной отправки нет**
5. Для `UNKNOWN` — запрос ордера по `client_order_id`. Нашёлся → досогласовываем статус.
   Не нашёлся → только тогда можно отправить повторно

Кнопка «Да» защищена от двойного нажатия: callback обрабатывается один раз, повторное
нажатие получает ответ «уже обрабатывается». Блокировка через Redis по ключу
`exec:lock:{user_id}:{signal_id}` с TTL.

## 9. SL и TP на бирже

BingX v2 позволяет передать `takeProfit` и `stopLoss` JSON-строками прямо в запросе
на вход — **проверить актуальный формат по живой документации/API перед реализацией**,
не по статьям в интернете.

Порядок:

1. Убедиться в режиме позиций (односторонний / хедж) и выставить `positionSide` корректно
2. Выставить плечо (`/openApi/swap/v2/trade/leverage`) до входа
3. Отправить маркет-ордер вместе с SL и TP

Если биржа приняла вход, но отклонила SL — это **аварийная ситуация**: позиция открыта
без стопа. Поведение: немедленно повторить постановку стопа отдельным условным ордером;
если и это не удалось — громкое уведомление «⚠️ ПОЗИЦИЯ БЕЗ СТОПА, символ, объём,
поставьте стоп руками» и запись в лог уровня ERROR. Не молчать, не ретраить бесконечно.

## 10. Сверка с биржей (reconciler)

Расширяет существующий `position_monitor`, отдельный воркер, интервал ~1 минута:

- Тянет открытые позиции и последние ордера
- `execution_orders` в статусе `UNKNOWN` — доразрешает по `client_order_id`
- Позиция закрылась по SL или TP → закрывает сделку в журнале: фактическая цена выхода,
  комиссии, `exit_reason = STOP_LOSS | TAKE_PROFIT`, уведомление
- Позиция закрыта руками на бирже → сделка в журнале тоже закрывается, помечается
  как закрытая вне бота
- Расхождение «в журнале открыто, на бирже нет» → уведомление, а не тихая правка

Журнал остаётся источником истории, биржа — источником истины по текущему состоянию.

## 12а. Наблюдение — ежедневная сводка исполнения

Между шагами 15.4 и 15.7 нужен период наблюдения. Чтобы он не превратился в «человек
должен постоянно смотреть», наблюдение автоматизируется: код накапливает факты, бот
отправляет одну сводку в сутки.

Реализуется на шаге **15.4** (когда ордера ещё не уходят) и живёт дальше без изменений.

**Что записывается по каждому сигналу READY:**

- показана ли карточка подтверждения
- решение пользователя: подтвердил / отказался / карточка истекла по TTL
- если отказ кода — `finding_code` гварда, который сработал
- расчётные цифры на момент карточки: цена, дрейф от цены сигнала, объём, нотионал,
  маржа, плечо, риск в валюте и процентах, RR
- на шаге 15.4 — что именно ушло бы на биржу (готовый `OrderRequest` в лог и в
  `execution_orders` со статусом, помечающим «сухой прогон»)

**Сводка раз в сутки (`daily_jobs`, час из `EXEC_DAILY_DIGEST_HOUR`):**

```
📊 Исполнение за сутки

Сигналов READY: 6
  подтверждено: 2
  отказ пользователя: 3
  истекло по TTL: 1

Отказы кода: 2
  MAX_POSITIONS — 1
  PRICE_DRIFT — 1

Средний расчётный риск: 0.9% (диапазон 0.7–1.0%)
Средний RR: 2.1
Средний дрейф цены на подтверждении: 0.12%

Аномалии: нет
```

Раздел «Аномалии» — главный. Туда попадает то, что человек глазами не поймает:

- расчётный риск отклонился от заданного больше чем на 10%
- объём после округления даёт риск меньше половины заданного (слишком мелкий лот)
- дрейф цены при подтверждении регулярно выше половины допустимого порога
- гвард срабатывает подозрительно часто (более половины сигналов)
- на шагах 15.5+ — расхождения между журналом и биржей, найденные reconciler

Если аномалий нет — так и пишем. Пустая строка тут не годится: человек должен видеть,
что проверка была и прошла.

**Отчёт по демо-периоду.** На шаге 15.6 reconciler дополнительно умеет собрать сводный
отчёт за произвольный период: сколько входов, сколько закрыто по SL, по TP, вручную,
фактический средний R, расхождения с журналом. Вызывается кнопкой, руками ничего не сводится.

**Роль человека сокращается до трёх действий:** посмотреть цифры в карточке перед «Да»,
раз в сутки прочитать сводку, среагировать на раздел «Аномалии».

## 13. Тесты

Обязательно до включения на реальном счёте:

- `sizing`: округление вниз, минимальный лот, нехватка маржи, нулевое расстояние до стопа
- каждый guard отдельно, включая порядок срабатывания
- идемпотентность: повтор при `UNKNOWN` не создаёт вторую позицию (мок биржи)
- «вход прошёл, стоп отклонён» → уведомление и попытка восстановления
- reconciler: закрытие по SL, по TP, ручное закрытие на бирже, расхождение
- переход сигнал → ордер → сделка в журнале с корректным `entry_reason` из сигнала
- сводка исполнения: подсчёты по подтверждениям и отказам, срабатывание каждого
  правила из раздела «Аномалии», корректная сводка при нуле сигналов за сутки

BingX-клиент в тестах замокан полностью. Ни один тест не ходит на биржу.
