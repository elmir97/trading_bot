# Открытие сделки из бота — план ядра и чат-мастера

Статус: **план, без кода** (05.10.2026). Основа — разведка Р1–Р8 на демо (`docs/handoff.md`, раздел
«Разведка открытия сделки на демо») и решения владельца 05.10. Mini App — отдельный план, вызывает то же
ядро. Live — шаги 1–6 плана live в handoff; открытие на live — первым пунктом шага 5.

## 0. Решения, на которые опирается план

- Мастер начинается с выбора: **«Открыть на бирже»** / **«Только записать в журнал»** (текущий мастер без
  изменений)
- Equity берётся с биржи (активный счёт из настроек), руками не вводится
- **Блокируют открытие:** нет стопа; риск выше максимума плана; дневной/недельный лимит убытка
  достигнут (жёсткий блок); плечо выше `max_leverage` плана; технические причины
- **Предупреждают** (кнопка «Открыть всё равно»): RR ниже минимального; монеты нет в белом списке;
  лимит сделок в день
- Стоп обязателен; позиция ни секунды не должна быть без стопа: стоп не встал — немедленно закрыть и
  уведомить
- Сделка в журнале — только после подтверждённого исполнения, с `orderId` входа
- Только демо; live — в общем плане live

Факты разведки, которые определяют устройство:

| Факт | Следствие |
|---|---|
| Р4: неверный вложенный стоп отклоняет весь вход (101400) | **стоп и тейк — вложенные в ордер входа** (`stopLoss`/`takeProfit`), и для маркета, и для лимита |
| Р3/Р6: вложенные SL/TP появляются отдельными ордерами через ~0.1 с, `clientOrderId` пустой, связь — `positionID` | read-back стопа — openOrders по `positionID` + тип + сторона + `stopPrice` |
| Р5: лимит — статус `PENDING`, SL/TP внутри ордера до исполнения; отмена по `clientOrderId` | у лимита свой жизненный цикл (WORKING), отмена — по `clientOrderId` |
| Р3а: смена режима маржи при позиции/ордерах — 104103 | режим ставится только при нуле позиций и ордеров по символу |
| Р2: демо приняло плечо 500 при максимуме 125 | проверка плеча — у нас, после POST — read-back |
| Р4: сторона стопа сверяется с **last price** | наша проверка — тоже по last, свежему |
| Р8: в истории исполнений `clientOrderID` пустой | свои исполнения импорт узнаёт только по `orderId` → он обязан быть в `execution_orders` |
| Р7: частичное исполнение на демо не воспроизводится | ядро страхует частичное само; проверка — на live (шаг 5) |
| BingX хранит `clientOrderId` в нижнем регистре | генерировать сразу в нижнем |

## 1. Решения по открытым вопросам (приняты владельцем 05.10, все шесть — «да»)

**1.1. Режим маржи по умолчанию — изолированная. Выбор — в «Настройках»** (одна настройка «Режим маржи
для новых сделок»: Изолированная / Кросс), на карточке показывается, в мастере не спрашивается.
- Изолированная: максимальный убыток при сбое стопа (гэп, отказ биржи) ограничен маржей позиции, а не
  всем счётом; ликвидация считается по позиции и предсказуема — её можно проверить против стопа до входа
- Кросс: ликвидация далеко, но провал стопа может съесть весь счёт; при одном пользователе и
  обязательном стопе выигрыша нет
- Каждый раз в мастере — лишний шаг без пользы: режим меняется редко, а при открытой позиции по символу
  его всё равно не сменить (Р3а)

**1.2. Риск с учётом комиссии** (вход + выход по стопу, тейкер). Объём = ⌊(equity × риск% − комиссии) / дистанция⌋ под шаг лота, где
комиссии ≈ объём × (цена входа + цена стопа) × ставка тейкера (с биржи, `commissionRate`). Так «риск 1%»
на карточке — честный убыток при срабатывании стопа. Решение — за владельцем (альтернатива: комиссия
отдельной строкой, риск только ценовой — как в мастере журнала сейчас). **Принято:** на карточке — риск в $ с
комиссией и отдельной строкой комиссия.

**1.3. Истечение лимита:** по умолчанию **4 ч**, в мастере кнопки **15 мин / 1 ч / 4 ч / 24 ч**. Ордер на
бирже — GTC, срок держит бот (таймер отмены). «До отмены» не предлагать: забытый лимит исполнится в
непредсказуемый момент.

**1.4. Запас ликвидации:** ликвидация дальше стопа минимум на **50% дистанции до стопа**
(|вход − ликвидация| ≥ 1.5 × |вход − стоп|). Мастер предлагает плечо, при котором это выполняется. **В отказе — максимальное плечо, которое пройдёт при
этом стопе:** «При стопе −3.00% ликвидация слишком близко: максимум 18x (запас 1.5×)». Формула (изолированная):
L_max = ⌊1 / (1.5·d + mmr)⌋, d — дистанция до стопа в долях, mmr — §5 п.6; не выше максимума биржи и плана.

**1.5. Отдельный флаг сухого прогона открытия** `EXEC_OPEN_DRY_RUN` (по умолчанию `true`) и
`EXEC_OPEN_ALLOW_LIVE` (по умолчанию `false`): общий `EXEC_DRY_RUN` на проде сейчас `false` — действия
этапа 4 живые на демо, и включать его ради открытия значит выключить их. Live открытия — только флагом
плана live.

**1.6. Только в пустую сторону.** Позиция по символу и стороне уже есть → блок на шаге «Сторона» и на карточке:
«По XRP-USDT уже открыт LONG 330 (вход 1.4952). Открытие из бота — только когда по этой стороне нет
позиции: добавь к ней в «Позициях» или закрой». (Добавление к позиции — не в этом релизе.)

## 2. Архитектура

```
app/execution/opening/
  calc.py       — чистый расчёт: объём, риск $, маржа, комиссия, RR, ликвидация ≈, проверки (без I/O)
  checks.py     — классификация нарушений: BLOCK / WARN (по решению 05.10), технические отказы
  service.py    — TradeOpeningService: prepare() → карточка, confirm() → исполнение, cancel(), expire()
  recovery.py   — восстановление незавершённых открытий (старт бота + каждый цикл)
  protect.py    — проверка стопа/тейка после исполнения, запасной стоп, аварийное закрытие
app/workers/openings.py — цикл лимитов: исполнение, частичное, истечение (15 с)
app/bot/handlers/open_trade.py — чат-мастер (тонкий: ввод → service → рендер)
```

dataclass-ы карточки и результата. Уведомления — через существующий отправитель (как reconciler).

## 4. Состояния открытия

```
CARD ──Открыть──► CONFIRMED ──► SUBMITTING ──► (маркет) FILLED ──► PROTECTED ──► DONE
  │                   │              │              │                    (сделка в журнале)
  │                   │              │              └─ стоп не встал ─► EMERGENCY_CLOSED / ALARM
  │                   │              ├─ (лимит) WORKING ──► FILLED …   (частичное — §6)
  │                   │              │            ├─ Отменить ─► CANCELLED
  │                   │              │            └─ срок ─► EXPIRED
  │                   │              ├─ отказ биржи ─► REJECTED
  │                   │              └─ нет ответа ─► UNKNOWN → (поиск по cid) FILLED | WORKING | NOT_PLACED
  │                   └─ проверка не прошла (плечо, режим, цена ушла) ─► REFUSED
  ├─ Отмена ─► DECLINED
  └─ 60 с без ответа ─► EXPIRED_CARD
DRY_RUN — при EXEC_OPEN_DRY_RUN: все проверки, строки execution_orders DRY_RUN, на биржу ничего
```

Переход статуса — всегда условным UPDATE (`WHERE id=? AND status=<ожидаемый>`), rowcount ≠ 1 — чужой
обработчик уже взял открытие.

## 5. Порядок исполнения (confirm)

Под Redis-локом `position_lock_key(user, symbol, side)` (тот же, что у действий этапа 4: reconciler и
монитор этот символ/сторону пропускают). TTL — с запасом на все шаги ниже, считается формулой как
`confirm_lock_ttl_seconds`.

1. `CARD → CONFIRMED` условным UPDATE (двойное нажатие — §8). Журнал нажатий — строка
   `execution_callbacks` с `trade_opening_id` до любой работы
2. **Повторные проверки на свежих данных:** гварды исполнения (флаги, режим счёта, права ключа, хедж-режим);
   equity/available; last price; карточка не старше 60 с. Объём пересчитывается: если риск $ или объём
   ушли больше чем на 10% (цена сдвинулась) — `REFUSED` с кнопкой «Пересчитать» (новая карточка)
3. **Стоп:** сторона по свежему last (LONG — стоп < last, SHORT — стоп > last); для лимита — и против
   цены лимита; дистанция ≥ `exec_min_stop_distance_percent`
4. **Режим маржи:** GET; совпадает — дальше. Не совпадает: позиций и ордеров по символу нет → POST + GET
   read-back, не сошлось — `REFUSED`; есть позиция/ордера → `REFUSED` «режим XRP — кросс, сменить нельзя
   при открытой позиции/ордерах» (Р3а)
5. **Плечо:** выбранное ≤ `maxLong/ShortLeverage` с биржи и ≤ `max_leverage` плана — иначе `REFUSED` до
   POST (Р2: биржа сама не откажет). Если по стороне есть позиция — плечо берётся с неё (менять плечо под
   открытой позицией не будем). Иначе POST по стороне → GET read-back: не равно выбранному — `REFUSED`,
   вход не отправляется
6. **Ликвидация ≈:** изолированная — LONG `liq ≈ E·(1 − 1/L + mmr)`, SHORT `E·(1 + 1/L − mmr)`, `mmr`
   консервативно 1% (на Р3 факт ≈ 0.41%); требование §1.4, иначе `REFUSED` с подсказкой плеча
7. **Вход:** строка ENTRY в `execution_orders` (PENDING, cid) — **commit до HTTP**; `SUBMITTING`; POST
   маркет или лимит с вложенными `stopLoss` (обязательно) и `takeProfit` (если задан), `workingType
   MARK_PRICE`
   - ответ `code≠0` → `REJECTED` (текст биржи), позиции нет (Р4)
   - таймаут/обрыв → `UNKNOWN` → поиск по cid (§7); **повторной отправки нет никогда**
8. **Маркет — read-back исполнения:** GET по cid → `FILLED`, `executedQty`, `avgPrice`, `commission`,
   `positionID`, время (`updateTime`). `FILLED`
9. **Защита (protect.py):** openOrders по символу, ищем `STOP_MARKET` с нашим `positionID`, стороной
   закрытия, `stopPrice` = нашему (с точностью цены), объём ≥ исполненного; тейк — так же. До 3 попыток
   через 500 мс (Р3: появляются через ~0.1 с). Найденные — строки STOP_LOSS / TAKE_PROFIT в
   `execution_orders` с `exchange_order_id` (нужно импорту: выход по стопу — `triggerOrderId` = наш стоп)
   - **стоп не найден / объём меньше позиции** → запасной стоп отдельным ордером: `STOP_MARKET`,
     `closePosition=true` + `quantity` = объём позиции (правило разведки 02.10), cid `…s`, read-back
   - **запасной стоп не встал** → **аварийное закрытие**: маркет reduce на весь объём позиции, cid `…c`,
     read-back позиции = 0 → `EMERGENCY_CLOSED`, уведомление «🚨 Стоп не встал — позиция закрыта
     маркетом», сделка в журнал **записывается** (вход и выход, причина «аварийное закрытие»)
   - **закрытие тоже не прошло** → `ALARM`: уведомление «🚨🚨 Позиция XRP LONG 10 БЕЗ СТОПА — закрой
     вручную», повтор каждые 15 с циклом §6 до стопа или нуля позиции
   - тейк не найден — не авария: предупреждение в итоговом сообщении, сделка открыта
10. **Ликвидация факт:** `liquidationPrice` из позиции. Ликвидация между входом и стопом → аварийное
    закрытие (стоп бесполезен); дальше стопа, но меньше запаса §1.4 — предупреждение в итоге
11. **Сделка в журнал** (одна транзакция): `Trade` source `BOT`, OPEN, `account_mode`, `entry_price` =
    `avgPrice`, `quantity` = исполненный, `fees` = |commission|, `stop_loss` = `initial_stop_loss`,
    `take_profit`, `leverage` (read-back), `risk_percent`/`risk_reward` от фактической цены,
    `account_balance_at_entry` = equity шага 2, `external_position_id` = `positionID`,
    `fill_confirmed=true`, `opened_at` = время исполнения; `TradeFill` ENTRY с `external_fill_id` =
    `orderId` входа; `execution_orders.trade_id`; `trade_openings.trade_id`, `DONE`
12. Сообщение: карточка сделки (как после мастера журнала) с кнопкой «Позиция» (экран действий этапа 4);
    переписка мастера удаляется (§9)

**Что подхватывают этапы 4 и 5 без правок логики:** сделка `BOT` с `account_mode` и `external_position_id`
связывается с позицией (`link_trade`), действия этапа 4 и уведомления этапа 5 работают от позиции.
**Правки по источнику `BOT`:** reconciler — ветка сделок бота (проверка «позиция без стопа» `STOP_MISSING`)
для `SIGNAL_EXECUTION` **и** `BOT`; `bot_fill_external_ids` и кнопки карточки — тоже оба источника.

## 6. Лимитный вход

- После POST: биржа `PENDING` → `WORKING`, `expires_at` = сейчас + срок. Сообщение «⏳ Лимит XRP LONG 10
  @ 1.4193 выставлен, стоп 1.3767, тейк 1.5390. Истекает 05.10 21:50 (UTC+5)» + **[Отменить лимит]**
- **Цикл `openings` (15 с)**, для каждого `WORKING` под локом позиции, GET по cid:
  - `PENDING`, срок не вышел — ничего
  - `PENDING`, срок вышел → DELETE по cid → GET read-back: `CANCELLED`, исполнено 0 → `EXPIRED`,
    сообщение «⌛ Лимит XRP LONG @ 1.4193 истёк через 4 ч и отменён. Позиция не открыта.» Карточка
    лимита правится, кнопка снимается
  - `FILLED` → шаги 8–12 §5
  - `PARTIALLY_FILLED` (или `executedQty > 0` при `PENDING`) → **сразу защита частичной позиции**: по
    `positionID` ищем стоп с объёмом ≥ позиции; нет — запасной `closePosition`-стоп (закрывает весь
    остаток, Р0в; при дальнейших исполнениях покрывает и их). Лимит стоит дальше. Сообщение «◐ Лимит
    исполнен частично: 4 из 10, стоп стоит». Сделка в журнал — когда лимит закончится (исполнен
    полностью / отменён / истёк) на фактический объём
  - полностью исполнен после частичного: если стоит и наш запасной, и вложенный стоп — запасной
    снимается (успех — повторным openOrders, как на этапе 4)
- **[Отменить лимит]** — та же ветка, что истечение: DELETE по cid → read-back. Исполнено 0 →
  `CANCELLED`; исполнено > 0 → защита + сделка на исполненный объём, сообщение «отменён остаток»
- Гонка «отмена ↔ исполнение»: DELETE вернул «order not exist»/`FILLED` → ветка исполнения, ничего не
  теряется
- Позиция по символу/стороне, открытая до лимита (ручная), смешается с исполнением лимита. **Блок на
  карточке:** по этому символу и стороне уже есть позиция — «открытие из бота только в пустую сторону»
  (иначе средняя цена, стоп и журнал перестают сходиться). Касается и маркета

## 7. Перезапуск посреди открытия (recovery.py)

Запускается **при старте бота до начала поллинга** и **каждые 15 с циклом `openings`**, берёт лок
позиции (занят — пропуск до следующего цикла). Обходит `trade_openings` в CONFIRMED / SUBMITTING /
WORKING / FILLED / PROTECTED. **Новый вход не отправляется ни в одной ветке.**

| Состояние после падения | Восстановление |
|---|---|
| CONFIRMED, строки входа нет | вход не уходил → `REFUSED` «прервано перезапуском», сообщение с «Пересчитать» |
| SUBMITTING / ENTRY PENDING или UNKNOWN (ушло, ответа нет) | GET по cid: `FILLED` → §5 шаги 8–12; `PENDING` → `WORKING`; `109421` и позиции по стороне нет — ждём ≥ 30 с от отправки (биржа могла не успеть), повторный 109421 → `NOT_PLACED`, сообщение «вход не выставлен» |
| FILLED (исполнение есть, защита не подтверждена) | §5 шаг 9: найти стоп по `positionID`; нет — запасной стоп; нет — аварийное закрытие |
| PROTECTED (сделка не записана) | шаг 11 (идемпотентно: `trade_id` уже есть — только `DONE`) |
| WORKING | обычный цикл §6 |

Входы открытия **исключаются из** `list_unresolved_entries` reconciler'а (фильтр `trade_opening_id IS
NULL`) — у них свой разбор, без 10-минутного окна этапа 15.

## 8. Идемпотентность и двойное нажатие

- `client_order_id` = `to{opening_id}u{user_id}{e|s|t|c}` (нижний регистр, ≤ 40): из одного открытия
  нельзя получить два разных входа; UNIQUE в `execution_orders` не пустит вторую строку
- «Открыть» дважды: второе нажатие получает rowcount 0 на `CARD → CONFIRMED` (или лок занят) → ответ
  «Уже открываю…» / текущий статус. Строка в журнале нажатий пишется у обоих
- Таймаут после отправки — не повтор, а поиск по cid (§7). Кнопка «Повторить» после `NOT_PLACED`/`REFUSED`
  — только через новую карточку (новый `opening_id`, свежий расчёт)
- Mini App вызывает тот же `confirm(opening_id)` — двойной тап там же гасится

## 9. Чат-мастер

Вход — «➕ Добавить сделку»: **[🟢 Открыть на бирже] [📝 Только записать в журнал]**. Второй — текущий
мастер. Первый — новые состояния `OpenTradeStates`:

| Шаг | Ввод | Подсказка/проверка |
|---|---|---|
| 1. Монета | текст | поиск по контрактам BingX (кэш публичного списка): точное `XRP` → `XRP-USDT`; иначе до 6 кнопок по префиксу/вхождению; нет — «не нашёл, попробуй ещё» |
| 2. Сторона | [LONG] [SHORT] | если по стороне уже есть позиция — блок сразу (§6) |
| 3. Тип входа | [Рынок] [Лимит] | текущая цена в тексте |
| 3а. Цена лимита | число | LONG-лимит выше last / SHORT ниже — предупреждение «исполнится сразу как рынок» |
| 3б. Срок лимита | [15 мин] [1 ч] [4 ч ✓] [24 ч] | |
| 4. Стоп | число, обязателен | сторона по last, дистанция %, «≈ ликвидация при плече N» |
| 5. Тейк | число / [Без тейка] | RR |
| 6. Риск % | [по плану 1.00%] или число | > максимума плана — сразу «нельзя: максимум X%» |
| 7. Плечо | [предложенное] [макс. по плану] или число | ≤ плана и биржи, запас ликвидации |
| 8. Карточка | — | ниже |

**Карточка подтверждения** (свежие данные, действует 60 с):

```
🟢 Открыть на бирже — DEMO
XRP-USDT LONG · Рынок (≈1.4950)
Стоп 1.4501 (−3.00%) · Тейк 1.5399 (+3.00%) · RR 1.00
Риск: 14.98 $ (1.00% от 1 500.00 $ equity), с комиссией
Объём: 323 XRP (≈482.89 $) · шаг 1
Маржа: 48.29 $ (изолированная, плечо 10x) · свободно 1 475.00 $
Ликвидация ≈ 1.3605 (в 3.0 раза дальше стопа)
Комиссия ≈ 0.48 $ (вход и выход по стопу)
⚠️ RR 1.00 ниже минимального 1.50
[Открыть всё равно] [Изменить] [Отмена]
```

Блокирующие нарушения — вместо кнопки «Открыть» список «🚫 …» и [Изменить] [Отмена]. [Изменить] —
возврат к шагу (кнопки полей). Карточка старше 60 с — кнопки отвечают «Карточка устарела» + [Пересчитать].

**После открытия:** переписка мастера удаляется (`WizardTrailMiddleware`: префикс состояний расширяется на
`OpenTradeStates`; карточка подтверждения не удаляется, а **правится** в итог — «✅ Открыто: XRP LONG 330
@ 1.4952, стоп 1.4501 ✓, тейк 1.5399 ✓, сделка #N» с кнопкой «Позиция»). Лимит: карточка правится в
«⏳ Лимит выставлен…» с [Отменить лимит]; исполнение/истечение — новым сообщением, карточка лимита
правится. Отказ — карточка правится в текст причины + [Пересчитать].

## 10. Ошибки и откаты (что видит пользователь)

| Ситуация | Код | Что делает ядро | Сообщение |
|---|---|---|---|
| нарушение BLOCK | `PLAN_*` | кнопки «Открыть» нет | список 🚫 |
| нет ключей / права / хедж-режим не тот | существующие гварды | `REFUSED` | как на этапе 4 |
| equity ≤ 0 / маржи не хватает | `INSUFFICIENT_MARGIN` | `REFUSED` | «нужно X $, свободно Y $» |
| объём < минимального после округления | `QTY_BELOW_MIN` | `REFUSED` | «минимум 2 XRP / 2 $ — увеличь риск или сократи стоп» |
| плечо > биржи/плана, read-back ≠ | `LEVERAGE_*` | `REFUSED` до входа | «плечо не выставилось: 20 вместо 10» |
| режим маржи не меняется | `MARGIN_MODE_*` | `REFUSED` до входа | Р3а-текст |
| стоп не с той стороны / ликвидация ближе запаса | `STOP_SIDE`, `LIQ_TOO_CLOSE` | `REFUSED` | с подсказкой |
| цена ушла (>10%) | `CARD_STALE` | `REFUSED` | [Пересчитать] |
| биржа отклонила вход | `REJECTED` | позиции нет | текст биржи |
| нет ответа на вход | `UNKNOWN` | поиск по cid | «проверяю, открылась ли позиция…» → итог |
| стоп не встал | `STOP_FAILED` | запасной → аварийное закрытие | 🚨 |
| аварийное закрытие не прошло | `ALARM` | повтор каждые 15 с | 🚨🚨 вручную |
| тейк не встал | — | сделка открыта | ⚠️ «тейк не стоит — поставь в «Позиции»» |

Плечо и режим, выставленные до отказанного входа, **не откатываются** (они не создают риска и останутся
для следующего входа); в сообщении — что изменено.

## 11. Тесты

- **calc / checks (чистые):** объём вниз под шаг (в т.ч. шаг 0.001, 1, 10), минимум qty/notional, риск с
  комиссией, маржа, ликвидация ≈ LONG/SHORT, запас, RR, классификация BLOCK/WARN по всем кодам плана,
  предложение плеча
- **service на фейковой бирже** (сценарии по шагам, проверка execution_orders/trade_openings/trades):
  маркет — норма; вложенный стоп не найден → запасной; запасной не встал → аварийное закрытие;
  закрытие не прошло → ALARM; тейк не найден; ликвидация ближе стопа по факту; отказ 101400; таймаут →
  UNKNOWN → найден FILLED / найден PENDING / 109421 ×2 → NOT_PLACED; режим маржи при позиции; плечо
  read-back ≠; плечо > max биржи; цена ушла; DRY_RUN — ни одного POST (фейк падает на POST)
- **лимит:** WORKING → FILLED; → EXPIRED; отмена; частичное → запасной стоп → полное → снятие запасного;
  частичное → истечение → сделка на частичный объём; гонка отмена/исполнение
- **восстановление:** каждое состояние таблицы §7, двойной запуск восстановления (идемпотентно), лок занят
- **двойное нажатие:** два `confirm` параллельно (asyncio.gather) — один POST; повтор после DONE
- **интеграция с журналом:** импорт за окно с исполнением входа/выхода по стопу бота — сделка не
  задваивается (orderId входа, `triggerOrderId` стопа); reconciler: сделка `BOT` — STOP_MISSING при
  снятом стопе, закрытие по стопу фактом биржи; действия этапа 4 по позиции сделки `BOT`; связь с позицией
  только по своему счёту
- **мастер:** `simulate_chat` — проход маркет/лимит, удаление переписки, устаревшая карточка, «Изменить»;
  `smoke_check` — новые заглушки клиента (`set_margin_type`, `place_limit_order`, поиск/отмена по cid,
  `get_commission_rate`), путь карточки и «Открыть» в DRY_RUN
- **миграция M5:** репетиция `--checksum --expect-columns …`, офлайн-SQL владельцу
