# Mini App открытия сделки — план

Статус: **подэтапы 0–2 в работе в ветке `miniapp`, без деплоя; на 15.10 сделаны 0.1–0.3, 1.1–1.5, 2.1 и 2.2, следующий — 2.3** (разбивка — §9а, «да» владельца 12.10). План — 05.10.2026; дополнен 08.10 — §6а подготовка сервера, §9 подэтапы и место в очереди; 12.10 — §5а экраны «как в Walt», одна форма, Lightweight Charts). Mini App — основной интерфейс открытия сделки, чат-мастер —
запасной путь. Оба вызывают одно ядро (`docs/open-trade-plan.md`): расчёт, проверки, плечо/маржа, ордер,
стоп/тейк, read-back, журнал. В Mini App своей торговой логики нет — только ввод, показ и вызов API.

## 1. Решения, которые предлагаю

| Вопрос | Предложение | Почему |
|---|---|---|
| Где хостить статику | **VPS, тот же Caddy и тот же домен, что и API** | один источник (нет CORS), один сертификат, деплой тем же `git archive`; страница, которая жмёт «Открыть» на бирже, не лежит у третьей стороны (кто управляет сайтом на Netlify — может подменить JS и слать запросы с вашим initData). CDN одному пользователю не нужен |
| Стек фронта | **один `index.html` + ES-модули на чистом JS + CSS, без сборки и npm** | экран один; нет цепочки сборки и зависимостей npm (меньше поверхность атаки и поломок); тема и кнопки — из Telegram WebApp SDK; правка = обычный коммит |
| Стек backend | **FastAPI + uvicorn, отдельный сервис `api` из того же образа**, другая команда запуска | те же модели, ядро и настройки; бот и API падают и перезапускаются независимо |
| Живой пересчёт | **на сервере** (`/api/open/preview`, задержка 300 мс после ввода), не в JS | числа карточки обязаны совпасть с тем, что исполнит ядро (Decimal, шаг лота, комиссия) — второй расчёт в JS рано или поздно разойдётся |
| Срок initData | **1 час** от `auth_date` для всех запросов | Mini App держит initData с момента открытия; час — достаточно для одной сделки, просроченный — «Откройте заново» |

**Уточнения владельца (05.10, «да» на оба плана):**
1. Истёкший initData (1 ч) — экран «Сессия истекла — закрой и открой заново»; введённые поля сохраняются (`localStorage` в try/catch, ключ по `telegram_id` из `initDataUnsafe`, только поля формы, без initData) и восстанавливаются при следующем открытии
2. После открытия из Mini App бот присылает в чат ту же карточку «✅ Открыто… сделка #N» с кнопкой «Позиция», что и чат-мастер (один рендер в ядре)
3. «Открыть» — `MainButton` → нативное `WebApp.showConfirm` (текст: символ, сторона, объём, риск $) поверх серверной карточки → `confirm`

## 2. Архитектура

```
iPhone Telegram ──HTTPS──► Caddy :443 (Let's Encrypt, <поддомен>)
                              ├── /            → статика /srv/miniapp (index.html, app.js, style.css)
                              └── /api/*       → api:8000 (uvicorn, только внутри compose-сети)
api ──► PostgreSQL, Redis (те же), BingX (через ExchangeFactory), Telegram Bot API (только отправка)
bot ──► как сейчас: поллинг, мастер, reconciler, монитор, цикл лимитов, восстановление открытий
```

- **`api` не запускает** поллинг, планировщик, reconciler, восстановление — только запросы. Фоновая
  жизнь открытия (лимиты, истечение, восстановление после падения) — в процессе бота, как в плане ядра.
  Если `api` упадёт посреди `confirm`, открытие довосстановит бот (§7 плана ядра) — состояние в БД, не в
  процессе. Исключение (1.5): быстрые повторы защиты B.1 после ALARM своего «Открыть» `api` запускает сам
  (`OpeningsWorker.retry_alarm`, без цикла `run`); упал — тревогу подхватит цикл бота (≤ 15 с), см. handoff
- Общие Redis-локи позиции — бот и `api` не исполняют одно и то же одновременно; двойной тап и
  параллельный вызов из чата гасятся тем же условным переходом `CARD → CONFIRMED`
- Сообщения в чат (итог открытия, исполнение/истечение лимита) шлёт ядро через Bot API — у `api` свой
  экземпляр `Bot` только для `sendMessage` (поллинга нет — второй getUpdates не возникает)
- `trade_openings.source = 'miniapp'`; журнал нажатий — `execution_callbacks` с `action = 'ma_confirm'`
  / `'ma_cancel'` и `trade_opening_id` (тот же аудит, что у кнопок)

**Новые зависимости:** `fastapi`, `uvicorn` (без `[standard]` — uvloop/httptools не нужны). Код:

```
app/api/
  main.py        — create_app() (uvicorn --factory), lifespan (Database, Redis, ExchangeFactory, Bot), без планировщика;
                   лог — logs/api.log (bot.log чек-апа не смешивается)
  auth.py        — проверка initData (§4), чистая функция
  deps.py        — состояние процесса, сессия БД, Depends → CurrentUser, ApiError {code, message}
  routes.py      — эндпоинты §3
  schemas.py     — pydantic-модели; Decimal → строка
miniapp/
  index.html, app.js, api.js, render.js, style.css
deploy/
  Caddyfile
```

`miniapp/` и `deploy/` в образ бота не нужны — в `.dockerignore`; Caddy монтирует их с диска сервера.

## 3. API

Все запросы — заголовок `Authorization: tma <initData>`. Ответ — JSON, деньги и цены строками (Decimal).
Ошибки — `{code, message}` с тем же текстом, что увидит чат-мастер.

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/health` | без авторизации: `{ok}` — для проверки деплоя, ничего о пользователе |
| GET | `/api/me` | счёт (DEMO/LIVE), equity, свободно, режим маржи по умолчанию, план (риск по умолчанию и максимум, `max_leverage`, мин. RR, белый список), флаги (`dry_run`, live разрешён), сроки лимита |
| GET | `/api/symbols?q=xr` | до 20 контрактов: символ, шаг лота, мин. объём/сумма, точность цены (публичный список, кэш 1 ч), макс. плечо — только из кэша `/api/market` (17.10: публичной ручки с максимумом у BingX нет) |
| GET | `/api/market/{symbol}` | last, mark, время; плечо по сторонам и максимум; режим маржи; есть ли позиция по стороне; ордера по символу; комиссия. Кэш: цена 2 с, остальное 30 с |
| POST | `/api/open/preview` | ввод → карточка (объём, риск $ с комиссией, комиссия, маржа, ликвидация ≈ и запас, RR, нарушения BLOCK/WARN, максимум плеча при этом стопе, тейк на 2R — `take_2r`, 17.10). **Ничего не пишет**, считает на кэше §`market` — дёшево |
| POST | `/api/open` | ввод → `trade_openings` CARD (`source=miniapp`), свежие данные с биржи → `{opening_id, card, expires_at}` (60 с) |
| POST | `/api/open/{id}/confirm` | `{accept_warnings}` → `TradeOpeningService.confirm`. Ждёт результат до 20 с; дольше (лимит, поиск по cid) — возвращает текущий статус, фронт опрашивает GET |
| GET | `/api/open/{id}` | статус, итог (сделка #, цена, объём, стоп ✓/тейк ✓, ликвидация), ошибка |
| POST | `/api/open/{id}/cancel` | отмена `WORKING`-лимита (ветка §6 ядра) |
| GET | `/api/open?active=1` | стоящие лимиты пользователя |

Проверка владения: каждый `{id}` — только `trade_openings.user_id` текущего пользователя, иначе 404 (не
403 — не подтверждаем существование). Ограничение частоты (в Redis, на пользователя): preview 5/с,
`open`/`confirm`/`cancel` 1/с — защита биржи и от залипшей кнопки.

## 4. Авторизация (каждый запрос)

По документации Telegram «Validating data received via the Mini App»:

1. Разобрать `initData` как query string; ключи уникальны (дубль — 401)
2. `hash` вынуть; `data_check_string` — остальные пары `key=value`, отсортированные по ключу, через `\n`
   (`signature` — участвует как обычное поле, как требует текущая спецификация; сверить по документации
   при реализации и тестом на настоящем initData)
3. `secret_key = HMAC_SHA256(key="WebAppData", msg=BOT_TOKEN)`; `expected = hex(HMAC_SHA256(secret_key,
   data_check_string))`; сравнение `hmac.compare_digest` — не совпало → 401
4. `auth_date`: старше 1 часа или из будущего больше чем на 60 с → 401 «Сессия устарела — откройте
   приложение заново»
5. `user` — JSON из подписанных данных; `telegram_id = user.id`. **Никаких user_id из тела, пути или
   заголовков.** `telegram_id` → `users`; пользователя нет → 403
6. Разрешён только владелец: `MINIAPP_ALLOWED_TELEGRAM_IDS` (по умолчанию пусто → API отвечает 403 всем;
   включается явно в override)

Логи: initData и hash не пишутся никогда; `telegram_id` — маской `mask_telegram_id`. Токен бота — только
из Settings. Повтор перехваченного initData в пределах часа возможен только при утечке с устройства или
из HTTPS — защита: HTTPS, без логирования, короткий срок, rate limit, подтверждение по `opening_id` своего
пользователя.

### 5а. Экраны «как в Walt» (решения владельца 12.10; заменяет макет и поток «Проверить» §5)

Walt — бывший Wallet in Telegram, вкладка перпетуалов. От Walt берём **экран рынка** (описание владельца 12.10, рынок
NEAR) и общий вид; **экран ввода сделки у Walt не видели** — он наш: одна форма (решение 2). Модель расчёта — наша.

**Решения (приняты 12.10):**
1. **Модель — риск, не сумма.** В Walt вводят сумму/маржу и плечо, объём = маржа × плечо, TP/SL необязательны. У нас —
   поле **«Риск» ($ или %)**, объём считает ядро от риска и стопа; **стоп обязателен** (без стопа кнопка неактивна,
   ядро BLOCK); **плечо меняет только маржу**, не объём. Режима «по сумме» нет
2. **Ввод — одной формой, все поля сразу** (не по шагам, как чат-мастер): монета, Лонг/Шорт, Маркет/Лимит, стоп, тейк,
   риск, плечо. Любое изменение → живой пересчёт объёма, маржи, RR, ликвидации, предупреждений. **Одна кнопка «Открыть»
   → подтверждение**
3. **График — Lightweight Charts** (TradingView, Apache 2.0), файл библиотеки лежит в статике `miniapp/` и раздаётся
   нашим Caddy — без CDN, CSP §5 не меняется. Линии уровней: вход, стоп, тейк, ликвидация; перетаскивание — позже

Поток: **Рынок** (как Walt) → «Лонг»/«Шорт» → **Сделка** (форма) → «Открыть» → **Подтверждение** → итог. Плюс вкладка
**Позиции**.

- Все поля видны сразу; дефолты — из `/api/me` (риск по плану, плечо предложенное) и `/api/market` (цена)

- Любое изменение поля, чипа, ползунка, переключателя → `POST /api/open/preview` через 300 мс после последнего изменения.

  приглушены. Для маркета пересчёт и при обновлении цены (раз в 3 с). Лимит preview 5/с (§3) не упирается

  кнопкой, тем же текстом, что в чате

## 6. Инфраструктура и деплой

**docker-compose.yml — два сервиса:**

```yaml
  api:
    build: .
    container_name: trading_bot_api
    command: ["uvicorn", "--factory", "app.api.main:create_app", "--host", "0.0.0.0", "--port", "8000", "--workers", "1", "--proxy-headers"]
    env_file: .env
    environment: { REDIS_URL: redis://redis:6379/0 }
    depends_on: { postgres: {condition: service_healthy}, redis: {condition: service_healthy} }
    mem_limit: 256m
    restart: unless-stopped
    # ports не публикуем: доступ только через caddy

  caddy:
    image: caddy:2-alpine
    container_name: trading_bot_caddy
    ports: ["80:80", "443:443"]
    volumes:
      - ./deploy/Caddyfile:/etc/caddy/Caddyfile:ro
      - ./miniapp:/srv/miniapp:ro
      - caddy_data:/data          # сертификаты — переживают пересоздание
      - caddy_config:/config
    mem_limit: 96m
    restart: unless-stopped
```

**Caddyfile** (`<поддомен>` — от владельца): `encode gzip`; заголовки — HSTS, CSP (§5), `X-Content-Type-Options
nosniff`, `Referrer-Policy no-referrer`; `handle /api/*` → `reverse_proxy api:8000`; остальное — `file_server` из
`/srv/miniapp`; `-Server`. Сертификат Let's Encrypt — автоматически (HTTP-01 на :80). Наружу — **только 80 и
443**; `api`, PostgreSQL, Redis — без `ports`. Пункт 4 чек-апа расширяется: слушают только 22, 80, 443 (+10050
zabbix).

### 6а. Подготовка сервера (дополнение владельца 08.10) — до первого деплоя `api`

1. **Swap 1–2 ГБ — отдельное «да».** `fallocate -l 2G /swapfile` (если ФС не умеет — `dd`), `chmod 600`,
   `mkswap`, `swapon`, строка в `/etc/fstab`, `vm.swappiness=10` в `/etc/sysctl.d/`. Проверка: `swapon --show`,
   `free -m`; диск — 28 ГБ, занято ~19%, 2 ГБ укладываются. Откат: `swapoff /swapfile`, убрать строку из fstab,
   удалить файл (удаление — по «да»). В чек-ап CLAUDE.md: «swap нет» → «swap N ГБ, used»; сборки и репетиции
   по-прежнему по порогу available ≥ 700 МБ (swap — подушка от OOM, не запас для сборки)
2. **Перед открытием 80/443 — проверка, только чтение, отчёт владельцу:**
   - firewall: сейчас ufw выключен сознательно (чек-ап 05.10). Наружу должны слушать только 22, 80, 443;
     10050 — агент Timeweb (`zabbix-agent-timeweb`), решение владельца 08.10: **не закрывать, пускать только с
     `92.53.116.12`, `92.53.116.111`, `92.53.116.119`** (`Server=` в `/etc/zabbix/zabbix_agentd.conf`; перед
     правилом сверить список ещё раз). `ss -tulpn`, `ufw status`,
     `iptables -S` / `nft list ruleset` (docker пишет свои цепочки — опубликованный порт контейнера обходит ufw,
     поэтому главное — п. ниже). Включение ufw (allow 22/80/443) — отдельное «да», с открытой второй
     ssh-сессией на случай ошибки
   - контейнеры: `docker ps --format '{{.Names}} {{.Ports}}'` — у `trading_bot_db` и `trading_bot_redis` нет
     опубликованных портов (`0.0.0.0:`/`:::`), у `api` — тоже; публикуют только `caddy` 80/443. Тест на compose:
     у `postgres`/`redis`/`api`/`bot` нет ключа `ports`
   - ssh: `sshd -T | grep -Ei '^(passwordauthentication|kbdinteractiveauthentication|permitrootlogin|pubkeyauthentication)'`
     — ожидание: password no, kbd-interactive no, pubkey yes, root — `prohibit-password` или `no`. Если пароль
     включён — правка `sshd_config.d/` отдельным «да», с проверкой входа по ключу из второй сессии ДО перезапуска
     sshd
   Любое отклонение — стоп, порты 80/443 не открываются до исправления

**Порядок деплоя Mini App** (после ядра 1–5 на проде, после §6а):
1. Владелец: A-запись `<поддомен>` → `147.45.111.10`; я проверяю `dig` с двух резолверов

4. `docker compose up -d api` → `/api/health` изнутри сети; логи
5. `docker compose up -d caddy` → лог выпуска сертификата; снаружи `curl https://<поддомен>/api/health` и
   `https://<поддомен>/` (с машины без перехвата — с этой машины исходящие на 80/443/8000 дают «Empty reply»
